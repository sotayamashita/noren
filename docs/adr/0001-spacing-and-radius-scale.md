# ADR-0001: Define Spacing and Radius on One 4px Scale

## Context

The landing page uses whatever Tailwind spacing step looked right at the time. Off-grid values such as `gap-1.5` (6px), `px-2.5` (10px), `gap-5` (20px) and `gap-10` (40px) sit next to on-grid ones. Radii come from the shadcn default: `--radius: 10px` multiplied by 0.6, 0.8, 1.4 and 1.8, which yields 6, 8, 14 and 18px.

Spacing and radius therefore live on two different rulers. Nested surfaces cannot satisfy "outer radius = inner radius + padding", so corners look uneven where surfaces sit close together. The install card (outer 14, inner 8, vertical padding 6) and the dropdown menu (outer 10, inner 8, padding 4) are two examples.

Nothing records why a value was chosen, so each new component is eyeballed against its neighbours. The repository has no earlier ADR on layout.

Constraints: `components/ui` is generated by shadcn and must not be edited by hand. `components/demo` imitates macOS and Slack chrome and needs values those products use. Checks already run through oxlint (`just check`, the hk pre-commit hook, the editor).

## Decision

Spacing and radius are integer multiples of one 4px base unit, chosen from a fixed ladder with a named role per step, and enforced by a local oxlint rule.

## Options Considered

- Option A (chosen): one 4px unit, a nine-step ladder with roles, radius tokens on the same unit, oxlint rules for both. Pros: spacing and radius share a ruler, so concentric nesting needs no arithmetic; the 2x group rule holds by construction; the check runs in the existing pipeline with editor feedback and per-line disables. Cons: the generated `components/ui` shifts by 2px per radius step; a local plugin and the `@oxlint/plugins` dev dependency are added.
- Option B: an 8px grid with fixed 24px padding and a fixed 24px radius, as recommended in a widely shared post. Pros: very few numbers to remember. Cons: an 8px grid cannot express a 28px button or 12px control padding; one padding value cannot separate the inside of a group from the outside, so hierarchy disappears; one radius makes nested corners look uneven.
- Option C: keep the shadcn default radii and only restrict spacing. Pros: no visible change to `components/ui`. Cons: spacing and radius stay on different rulers, so every nesting needs fractional arithmetic and the install card and dropdown stay uneven.
- Option D: enforce with a standalone script (`scripts/check-spacing.ts`). Pros: simpler to write. Cons: a second checker outside oxlint with its own invocation, no editor feedback and no per-line disable.
- Option E: document the rule without checking it. Pros: no code. Cons: each new component drifts back to eyeballing.

## Consequences

### Scale and enforcement

The ladder for spacing is 1, 2, 3, 4, 6, 8, 12, 16 and 24 units (4, 8, 12, 16, 24, 32, 48, 64, 96px):

- 1 (4px): between glyphs, such as an icon and its chevron.
- 2 (8px): inside a control; between siblings in one group.
- 3 (12px): inline padding of bordered controls; between bordered controls.
- 4 (16px): between groups; page inline margin.
- 6 (24px): heading to content; card padding; around borderless controls.
- 8 (32px): between blocks within a section.
- 12 (48px): hero top padding on mobile.
- 16 (64px): between sections.
- 24 (96px): page bottom padding.

The gap between groups is at least twice the gap within a group; the ladder is arranged so this holds by construction (8, 16, 32, 64).

Radius uses the same unit. `app/globals.css` defines `--radius-sm` through `--radius-3xl` as `calc(var(--spacing) * n)` with n = 1, 2, 3, 4, 6, 8: sm (4px) for tags, kbd and inline code; md (8px) for buttons, inputs and menu items; lg (12px) for menus, popovers and tiles; xl (16px) for cards and windows; 2xl (24px) for the hero and other large surfaces; full for pills and avatars. Nested surfaces follow "outer radius = inner radius + padding". Past 24px of padding the layers count as separate surfaces.

Enforcement: a local oxlint JS plugin, `tools/oxlint/design-scale/` (`index.ts` plus one file per rule under `rules/`), registered in `oxlint.config.ts`. It reads `className` string literals, template literal quasis and the string arguments of `cn()` and `cva()`. The `spacing` rule reports any padding, margin, gap or inset utility whose step is not on the ladder; the `radius` rule reports any `rounded-*` utility that bypasses the tokens with an arbitrary value. `components/ui` stays ignored. The original decision excluded all of `components/demo`; [ADR-0002](./0002-content-components-and-gallery-boundaries.md#design-scale-enforcement) narrows that exception to spacing in named reproduction files. Radius checks remain enabled in those files. The ladder is also written into `AGENTS.md`.

### Impact and review conditions

Easier: picking a value becomes picking a role; nested radii come out concentric; the rule is visible in the editor before review.

Harder: a step outside the ladder must be argued into a role rather than added; the local plugin has to track oxlint plugin API changes.

Risks: the radius token change shifts the generated `components/ui` by 2px per step (buttons stay at 8px; cards 14 to 16; menus 10 to 12; sm 6 to 4). The rule only sees string literals, so class names built at runtime bypass it.

Original migration changes, using the paths at the time of this decision: `components/section.tsx` heading gap `gap-5` to `gap-6`; `components/sections/steps.tsx` step gap `gap-5` to `gap-4` with the inner `gap-1` kept; `components/sections/install-command.tsx` tab strip `py-1.5` to `py-2` and tabs `px-2.5` to `px-3`; `components/sections/github-stars.tsx` badge `py-0.5` to `py-1`; `app/globals.css` radius tokens as multiples of `--spacing`. Font weights on the landing page are limited to 400, 500 and 600; 700 remains only on Slack author names in `components/demo`.

ADR-0002 later removes `components/section.tsx` and moves the guide widgets from `components/sections/` to `components/guide/`. These historical paths are not current editing locations. The 4px scale remains in force, so this ADR is not superseded in full.

Revisit when: a shadcn regeneration changes how `components/ui` consumes `--radius-*`; oxlint changes its JS plugin API; a second product surface (docs, dashboard) needs a denser scale; or a design refresh changes the base unit.

## Advice

A post arguing for an 8px grid, strict 24px padding and a consistent 24px radius as guardrails for model-generated UI was reviewed (shared as a screenshot on 2026-09-06; author and URL not recorded). Its stance of few, explicit constraints is adopted. Its numbers are not, for the reasons under Option B.
